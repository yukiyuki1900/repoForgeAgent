# 设计决策

记录几个关键取舍，以及不这么做的代价。

## 1. 检索单位是符号与依赖闭包，不是文本片段

`src/graph.ts` 用 ts-morph 建立语义图，模块解析直接交给 TypeScript 编译器，因此 tsconfig `paths`、`baseUrl`、index 解析、扩展名补全全部由编译器负责。TS 认不了的扩展名（`.vue`）走手工回退。

这不是锦上添花。早期的正则实现只认相对路径，在使用 alias 的仓库上依赖图会大面积残缺，循环依赖检测形同虚设：

| 用例 | 正则实现 | AST 实现 |
|---|---|---|
| `02-alias-cycle` | **0 依赖边，0 个环** | 2 依赖边，1 个环 |
| `03-dynamic-import-cycle` | 1 依赖边，0 个环 | 2 依赖边，1 个环 |
| `04-arrow-component` | 1/2 组件（漏 `Card`） | 2/2 组件 |
| `05-jsx-render-edge` | 无 render 边 | 产出 render 边 |
| **通过率** | **1/5（20%）** | **5/5（100%）** |

在一个 319 文件的真实 Vue 仓库上，接入 AST 与 Vue SFC 解析后依赖边从 618 涨到 936；补上构建配置里的 alias 后又多回 80 余条。

## 2. alias 静态提取，不执行配置文件

前端项目普遍只在 `vite.config` / `webpack.config` 里写 alias，而不同步到 tsconfig。只读 tsconfig 会漏掉大量依赖——实测那个 Vue 仓库因此丢了 84 处导入，且全部集中在 pages / components / layouts 这些最关键的位置。

所以 `src/alias.ts` 会解析构建配置，但**只做 AST 提取，不执行文件**：配置是别人的代码，执行它既不安全，也会因为依赖环境变量、插件、动态导入而频繁失败。

代价是覆盖不了动态生成的 alias。支持的写法：

- 对象字面量 `{ "@": path.resolve(__dirname, "src") }`
- 数组形式 `[{ find, replacement }]`
- 简写属性 `resolve: { alias }` 配合同文件内的变量声明
- 包一层函数调用，如 `fileURLToPath(new URL("./src", import.meta.url))`

路径从表达式内的字符串字面量按序拼接得到——静态执行 `path.resolve` 不现实，但路径信息全在字面量里。

匹配规则与 `@rollup/plugin-alias` 一致（整体相等或落在路径边界），否则 alias `"@"` 会把 `@vue/compiler-sfc` 这类 npm 包一并吃掉。

## 3. LLM 只负责解释，不负责计算

| 确定性代码 | LLM |
|---|---|
| 依赖图、循环依赖（Tarjan） | 架构分层推断 |
| 复杂度、耦合度、类型占比 | 依赖环的危害解读 |
| **环上最适合切断的边**（按引用次数最少选取） | 技术债优先级排序 |
| 问题聚合与风险分级 | 人类可读的架构叙述 |

循环依赖是图论问题，问模型既慢又不准还不可复现。

同理，循环依赖的 `evidence` 必须是**真实存在的回路**——早期版本直接把 Tarjan 的出栈顺序拼成路径，但相邻两项之间未必有边，等于在给模型喂假事实。现在会在强连通分量内 BFS 搜一条真实回路。

## 4. 上下文是压缩过的，且裁剪不静默

符号图直接序列化会轻松几十万 token。`src/narrate.ts` 把它压成分层摘要：目录级聚合、top-N 热点、环及建议切点、按规则聚合的问题统计。

裁剪预算集中在 `LIMITS` 常量，`truncated` 字段**显式记录每个类目被裁掉多少**，prompt 里也要求模型不要把已列出的当成全部。

裁剪必须逐层做：`LIMITS.cycles` 只限制环的**条数**，而单个强连通分量可能包含上千文件——实测 3000 文件的环会让摘要膨胀到 15k tokens。加上 `cycleFiles` 上限后，10000 文件、单环包含全部文件的极端仓库，摘要仍稳定在 ~600 tokens。

## 5. LLM 缺席不影响流水线

未配置模型或调用失败时降级为纯确定性分析，报告里明确写出「未配置模型」，而不是静默少一节。查询计划同理：有模型时用 LLM 翻译意图，否则回退规则解析。

## 6. 没有事实就不给结论

- 维护性评分只统计**真实计算出来的维度**。早期版本给重复代码率、依赖健康度硬编码了满分 100，导致任何仓库的总分都被系统性拉高
- 空仓库返回 0 分而不是靠分母兜底造出一个「健康」的 67 分
- 扫不到任何源码文件时直接失败，而不是产出一份 0 文件的空报告——绝大多数情况是路径指错了
- 前端只在**从未取得过真实数据**时才回退演示数据，否则会出现最误导的组合：真实的失败提示配一份伪造的健康报告

## 7. 用 LangGraph 而不是直接串函数

理由只有两个：四个独立分析器的**并行 fan-out / fan-in 与状态归并**（`findings` 通道用 concat reducer 汇聚各分析器产出），以及节点级的进度事件与状态快照。

有个坑值得记：`currentStep` 这类被多个并行节点写入的通道**必须显式给 reducer**，否则默认的 `LastValue` 通道一步只接受一个值，会抛 `InvalidUpdateError`。

进度事件从自定义的 node 包装里发出，而不是用 LangGraph 的 `streamEvents`——这样能拿到每个节点自己的产出摘要，也不受框架内部 API 变动影响。副产品是并行分析器的 start 事件会交错出现，本身就是「并行是真的」的现场证据。

## 8. 浏览器不给绝对路径，就让同机后端反查

目录选择用 `showDirectoryPicker()` 而不是 `<input webkitdirectory>`：后者会枚举目录下所有文件，前端项目的 `node_modules` 动辄十几万个文件，选中瞬间页面就卡死。

两者都拿不到绝对路径，但服务就跑在同一台机器上——前端把目录名与**顶层条目 + package.json 内容哈希**发过去，后端在文件系统里定位即可。

判据强弱差别很大：只比对顶层条目名时，同名项目结构高度雷同（都有 src、package.json、README），完全区分不出来；而同名项目的依赖与版本号几乎不可能逐字节一致，内容哈希命中即可认定是同一目录。

## 9. 改造只做能被编译器证伪的变换

循环依赖的一般性修复——提取共享模块、依赖倒置——本质是架构决策，要回答「代码该搬到哪里」。这类问题只能靠模型生成代码，既有幻觉风险，改完也无法证明行为不变：`tsc` 通过不等于运行时正确。

`import type` 不一样。它是**语义等价的机械变换**：判定靠 TypeScript 自己的引用分析（每一处引用是否都落在类型位置），改造是 ts-morph 的一个 API 调用，效果可以用「重跑 Tarjan，环是否消失」直接验证。整条链路上没有一个环节需要模型的创造力。

判定一律从严：只要有一处引用落在值位置就不改；命名空间导入、副作用导入、混用内联 `type` 修饰符、`emitDecoratorMetadata` 下使用装饰器的文件，一律拒绝。宁可漏改，不能误改——误改会把能跑的代码改坏，而漏改只是少一条建议。

## 10. 「能编译」不算验证通过

`--apply` 的验证分两层，缺一不可：

**类型层**判据是**不新增**错误，而不是零错误。真实仓库的 `tsc` 几乎从来不是干净的，要求零错误等于这个功能永远不会执行；但基线里已有的错误也不能拿来掩盖新引入的问题，所以改造前后各做一次全量 pre-emit 检查，按「文件 + 行 + 错误码 + 文本」做差集。

**结构层**要重新扫描仓库、重建依赖图、重跑 Tarjan，实测环数必须与 dry-run 的预测**完全一致**。只看编译是不够的——把 `import` 改成 `import type` 永远都能编译，但不一定真的打破了环。预测 3→1 而实测 3→2，说明工具对依赖边的理解是错的，哪怕代码跑得起来也要回滚。

这一层立刻见了效：接上结构验证的第一次运行就红了——模拟说改完 0 个环，实测仍是 1 个。根因在分析器自己：`extractDependencyEdges` 把所有 import 声明一律记为 `import` 边，包括 `import type`。而 `import type` 在编译期被整条擦除，运行时根本不存在这条依赖，于是循环依赖检测虚报了一批运行时不存在的环。修法是把纯类型导入记为 `type-reference` 边（fixture 16、17 锁定行为，后者覆盖 `verbatimModuleSyntax` 下内联 `type` 修饰符**不会**被擦除的例外）。

一个只用来「证明改动没问题」的验证环节，先证明了分析本身有问题——这正是它该有的样子。

## 11. 回滚交给 git，不自建快照

写入前的前置检查确保目标文件已被 git 跟踪且没有未提交改动，验证失败时 `git checkout --` 就是最可靠的还原。自己维护快照要处理权限、符号链接、并发写入，而这些 git 都已经做对了。

代价是：不在 git 仓库里、或目标文件有未提交改动时，直接拒绝执行而不是降级。这是有意的——没有可靠回滚手段就不该动用户的代码。

无论成功还是回滚，`refactor.diff` 与 `verify-report.md` 都会落到 `.reposurgeon/refactors/<时间戳>/`。回滚场景下这份 diff 尤其重要：它是「工具想改什么、为什么没通过」的唯一记录，人工复盘要靠它。

## 12. 先量再决定路由什么

整条流水线长这样，决策点只有一个：

```
START → loadRepository → scanFiles → detectStack → plan     ← 决策点
                                                     │
                                              parseSemantic
                                                     │
                       ┌─────────────┬───────────────┼───────────────┐
              analyzeArchitecture  dependency     quality      deadExports  ← 条件 fan-out
                  （可裁剪）        （恒在）       （恒在）        （可裁剪）
                       └─────────────┴───────────────┴───────────────┘
                                                     ▼
                                          retrieveContext              ← 有问题才进
                                                     ▼
                                                  narrate              ← 唯一的 LLM 节点，可裁剪
                                                     ▼
                                                  render → END
```

给流水线加决策节点，最容易滑向表演：每个节点前面挂一个条件判断，看起来「很 Agent」，实际一秒都没省。

所以先量。319 文件的 Vue 仓库，一次全量分析约 23 秒：

| 节点 | 耗时 | 占比 |
|---|---|---|
| `narrate` | 18156ms | **79%** |
| `parseSemantic` | 4737ms | 21% |
| 其余 8 个节点合计 | ~160ms | <1% |

结论直白：**四个确定性分析器加起来 35ms，路由它们是自欺欺人**。真正值得决策的只有 LLM 节点。`plan` 因此只在有真实成本差异的地方做取舍——问「有没有循环依赖」时跳过 `narrate`，23 秒降到约 4.9 秒，token 归零。

另外两条边界：

- **`dependency` 与 `quality` 不可裁剪。** 报告的 `metrics` 与循环依赖是必填内容，跳过它们等于产出一份残缺却看不出残缺的报告——比慢更糟。
- **决策用规则，不用模型。** 意图分类是低维、可枚举、要求可复现的判断。交给 LLM 只换来延迟、不确定性，以及「幻觉出一个不存在的节点名」这种能让整张图崩掉的风险。`createAnalysisGraph({ planner })` 留了注入点，想换成模型或做 A/B 对照都可以，但默认不锁死在模型上。

这和第 3 节是同一条线：LLM 负责解释，不负责计算，**更不负责控制流**。

## 13. 「跳过」必须是真的没执行

第一版把 `retrieveContext` 当成固定的 fan-in 汇聚点：没有检索问题时它照样被调度，只是内部直接返回空结果。于是出现了自相矛盾的输出——进度条上有一个耗时 0ms 的 `retrieveContext`，报告里却写着「本次跳过 retrieveContext」。

改法是让四个分析器的条件边指向同一个下一站：有问题去 `retrieveContext`，没有就直接去 `narrate` 或 `render`。多个分支返回同一目标即构成 fan-in，该节点只执行一次。

这类不一致比性能问题更值得修。工具说的话如果和它做的事对不上，使用者就再也无法凭输出判断任何事情。

顺带记一个 LangGraph 的细节：条件边的目标列表必须是字面量类型（`as const`），写成 `string[]` 编译不过。这层校验很有用——它能在编译期挡住「路由到一个拼错的节点名」。

## 14. 可选依赖不该拖垮主流程

`better-sqlite3` 是原生模块，会在换了 Node 大版本没重编译、CI 镜像缺构建工具链、只读文件系统这些场景下不可用。它此前是 `storage.ts` 的顶层静态导入，一旦加载失败整条分析流水线跟着崩——用户明明只想要一份 Markdown 报告，却因为一个可选的加速索引拿不到任何东西。

现在改成惰性加载 + 一次性探针：`require` 成功不代表能用（原生绑定是第一次构造时才 dlopen 的），所以用一个内存库试一次，把失败收敛到单点，然后告警并继续。

判断依据是**这个东西是不是主产物**。报告是交付物，SQLite 索引只是让看板能加载历史结果的加速层。同样的逻辑早先已经用在 `@vue/compiler-sfc`（只分析 React 项目的人不该被 Vue 编译器卡住）和 LLM 调用（模型失败降级为纯确定性分析）上。

## 15. 交出控制权的前提是「做错了代价可控」

项目里有两处涉及模型，处理方式截然相反：

| | `ask` | `refactor --apply` |
|---|---|---|
| 谁做决策 | 模型自主决定查什么、查几轮 | 确定性代码，模型完全不参与 |
| 最坏情况 | 查了一堆无关的东西，浪费几千 token | 改坏本来能跑的代码 |
| 兜底手段 | 只读工具 + 轮次上限 + 答案带行号可核对 | 类型检查 + 环数对账 + git 回滚 |

判据不是「这个任务难不难」，而是**这一步做错了，代价是什么**。查错方向可以再查一次；改错代码可能几周后才在生产环境暴露。

所以 `ask` 的七个工具全部只读，没有任何一个能写文件、跑命令或发网络请求。最坏情况下模型把七个工具轮流调满八轮，代价是一次无效的 API 调用。

## 16. 工具设计的四条经验

`ask` 的工具层比 prompt 更影响回答质量。踩下来有四条：

**只暴露索引，不暴露文件系统。** 工具只能查 `index.files` 里的路径，天然挡掉了路径穿越——不需要写 `..` 校验，因为根本没有一条通往 fs 的路。这比「加一层路径白名单」更可靠，因为它不是一道可以被绕过的检查，而是能力上就不具备。

**查不到时给候选，不给空结果。** 模型经常写出 `utils/request.ts` 这类差不多但不对的路径。返回 `not found` 它只会换个名字继续猜，白烧两轮；返回最接近的五条路径 + 一句「从中选一个重试」，它下一轮就能自我纠正。`resolvePath` 因此做了三级匹配：精确 → 后缀唯一命中 → 模糊候选。

**截断必须写进返回值。** 每个列表工具都限制条数，但更重要的是返回 `total` 与 `truncated`。静默截断会让模型把「前 40 条」当成全部，然后给出一个自信的错误结论——这比返回错误更危险，因为看不出来。同样的原则早先已经用在 `narrate` 的上下文压缩上。

**越界夹紧而不是报错。** 模型对行数的估计经常偏大（`readSource(path, 1, 9999)`）。直接报错是在惩罚一个无害的猜测，夹紧到文件范围并说明实际返回了多少，才是有用的行为。

## 17. Agent 的评估要分层

「给 agent loop 做回归测试」听起来不可能——模型不确定，同样的输入两次结果不同。但不可复现的只是**回答文本**，控制流和工具行为都是确定的：

- **工具层**：给定仓库，每个工具的返回值完全可预期。路径写错要给候选、行号越界要夹紧、截断要如实标注——这些能像普通函数一样测死。
- **循环层**：用桩模型（`MockLanguageModelV1`）按脚本返回工具调用，测的是**控制流**——轮次上限有没有生效、工具报错后循环能不能继续、撞上限时有没有如实标注。
- **回答质量**：这一层才真正需要模型，不进 CI。

这样切分之后，`tests/tools.test.ts` 里 12 条用例全部是确定性的、秒级的、不花钱的。真正会出问题的地方——工具返回了错误的事实、循环失控烧光预算——恰恰都在能测的那两层里。

## 18. 等待也要有反馈

一次追问要跑十几秒。早期版本里这段时间界面上只有一个转圈，然后回答「啪」地一次性出现——用户无从判断是在正常工作还是已经卡死，只能盯着屏幕猜。

改成 `streamText` 之后分两层填这段空白：前半程靠工具调用（每查一次就多一行，还顺带展示了推理路径），最后生成回答的那几秒靠文本增量。

有两个细节值得记：

**流式推的是过程，最终结果以 SDK 汇总的为准。** 多步调用时中间轮次也可能吐字，累积的增量未必等于最后那段回答。所以前端在流式期间显示累积值，拿到最终结果后换成 `result.answer`。把增量当成唯一真相，遇到「模型先自言自语再给结论」的情况就会串味。

**文本增量不进事件数组。** 一段回答几千个 token，逐条塞进 `record.events` 会让内存和回放体积一起失控，而它们的信息量完全等价于拼接后的字符串。所以 `TaskRecord` 单独留一个 `text` 字段累积，SSE 用独立的 `delta` 事件推送；中途接入的订阅者先收到一条带 `replace` 标记的全量，之后再接增量。

**工具事件带参数和返回值，但返回值是预览。** 事件结构原本是三种模式共用的最小公约数——`{channel, label, detail}`，工具通道被压到了「一个名字加一句摘要」。归并的价值在于「都是一条带标签的时间线」这个共性成立，不在于所有通道必须一模一样，所以 `tool` 加了一组可选字段，而不是把 JSON 塞进 `detail` 变成一坨文本。

返回值必须截断，因为它要同时进三个地方：`record.events`、SSE 推送、**以及每次断线重连的整份回放**。`readSource` 单次就是 4KB 上下，一轮问答十几次调用，不截断的话这三处一起放大。截断量如实报告——静默截断会让人以为看到了全部，然后基于半份数据下判断，这个教训在给模型的上下文那层已经付过一次代价。

回填返回值用的是给每个 `execute` 包一层，而不是给十几个 `record()` 调用点各加一个参数：**加参数要靠人记得传，包装不用**，而漏传的那种失败是静默的——事件照发，只是少了半边信息，没有任何东西会因此变红。同一层里 `onCall` 被 try/catch 包住，它最终会写进一条随时可能已经断掉的 SSE 连接，**观察者的失败不能改变被观察者的行为**。

**超时该由谁管，取决于谁知道真相。** 第一版前端设了一道「90 秒没收到进度就判定卡死」，那是错的，而且错得有连锁后果：任务快慢只有服务端知道（`narrate` 单节点就要 18 秒，合法的慢任务完全可能长时间没有事件），前端拿这个当指标必然误杀；更糟的是它宣布超时之后**没有通知服务端**——任务继续在后台烧 token，而界面同时给出了「重试」按钮，用户一点就变成两个任务并行。

改成各管各的：**业务超时归服务端**（分层设置，见 [18.5](#185-超时该由谁管取决于谁知道真相)）；**前端只判断一件自己有资格判断的事——链路通不通**。

依据是定频心跳，不是进度间隔：服务端每 15 秒往流里发一个 `ping` 事件，前端三个周期收不到才判定断线。**这个阈值是有依据的，而「多久没进度」那种阈值只能靠猜。** 心跳发成具名事件而不是 SSE 注释行（`: ping`），因为注释行浏览器会吞掉、JS 侧感知不到——那样只能保活中间代理，帮不了前端判断。

判定断线后**不调 cancel**：用户没有表达任何停止的意图，只是我们看不见了。任务该继续跑，由服务端的超时兜底。相应地这种情况也不提供重试入口——真失败了该给重试，而这里再点一次只会起第二个任务。**「任务失败」和「我看不见了」该给的选项不一样。**

**等待中的反馈不设阈值，也不写文案。** 早期设想是「超过 3 秒才显示『正在思考』」，两处都错：阈值让界面在短等待时装作没在等，那是隐瞒不是优雅；而「正在思考」是在**断言原因**——可能模型在想、可能工具在跑、也可能字已经在网络上了，文案一旦说错比不说更糟。现在是三个点的循环动画，只声称「还活着」，这是唯一一件能保证为真的事。

## 18.5 超时该由谁管，取决于谁知道真相

第一版只有一道全局五分钟。它的病根不是「长」，是**没有依据**——而且一个值同时承担了两种职责。

**总时长必然两头不讨好。** 总时长 = 各步骤之和，而步骤数本身是动态的：`ask` 的轮数由模型决定（1 轮和 8 轮差 8 倍），`analyze` 的节点由 `plan` 裁剪（跑满 23 秒、裁剪后 4.9 秒）。给一个方差这么大的分布设固定阈值，只会同时「偏短」（撞满 8 轮的 ask 要 8 分钟，被误杀）和「偏长」（正常情况的 13 倍，卡死了也要等五分钟）。

单步则是同质的：一次模型调用、一次 git 命令，各自的耗时分布稳定得多。所以职责重新划分：

| 层 | 防什么 | 阈值 | 依据 |
|---|---|---|---|
| 单次模型调用 | 网关吞了请求 | 60 秒 | 实测最慢的 `narrate` 18156ms，3 倍余量 |
| 单条 git 命令 | 仓库锁被占 | 10 秒 | 正常是毫秒级 |
| 总时长 · analyze | 兜底回收 | 5 分钟 | 60（narrate）+ 73（同步部分）= 133s，×2 |
| 总时长 · ask | 兜底回收 | 10 分钟 | 480（8 轮 × 60）+ 73（建索引）= 553s |
| 总时长 · refactor | 兜底回收 | 10 分钟 | 两次全量类型检查 + 重扫 ≈ 300s，×2 |

**但总时长不能取消**，原来那句「在最外层设一道比在每个地方各设一道更可靠」只对了一半。对的部分是：大部分步骤**根本打不断**——ts-morph 建图、`getPreEmitDiagnostics`、Tarjan 全是同步 CPU 密集，一旦开始任何 signal 都停不了它，总时长是它们唯一的防线。错的部分是不该**只有**这一道。

**单步超时到位之后，总时长就不用拍脑袋了**，它有了确定的形式：

```
总时长 = Σ(可打断步骤的上限)  +  Σ(打不断步骤的最坏耗时)  ×  安全系数
         ↑ 已经有硬上限，不用估      ↑ 唯一需要估的东西
```

唯一要估的是同步 CPU 那部分：实测 319 文件的 Vue 仓库同步部分约 4.9 秒，按支持到 10 倍规模、ts-morph 建图有超线性成分保守取 15 倍 → 约 73 秒。`ask` 那一行没乘安全系数，因为 553 秒里 480 秒**已经是硬上限**（8 个 60 秒），对确定的部分再乘 2 是虚胖。

**下界由合法最坏路径决定**（短于它就误杀正常任务，原来那个五分钟对 `ask` 正是这个毛病）；**上界由内存决定**（一个 running 任务攥着整个 `CodebaseIndex`，卡死的任务要占着它直到超时）。这也是为什么总时长可以定得宽：**它不服务于用户体验，只服务于资源回收**——服务用户体验的是另外两件事，界面上一直有反馈、随时能停，那两件到位之后 5 分钟还是 10 分钟用户根本感知不到，他早就点停止了。

推导过程写在 [src/limits.ts](../src/limits.ts) 里而不只是这里，因为下一个改这几个数的人打开的是代码。公式里还剩一个未知数——同步部分随规模怎么增长目前只有一个数据点，那个 15 倍系数是猜的。

**SSE 是传输格式，EventSource 是浏览器给它配的一个客户端——换掉的是后者。** 这两件事经常被混为一谈，而混淆的代价是把「客户端的缺陷」误记成「协议的缺陷」。`text/event-stream` 那套分帧没有任何问题（OpenAI、Anthropic 的流式接口用的都是它，Anthropic 的 `content_block_delta` 这类结构化事件也全放在 `data:` 里）。信封只负责三件事：分帧、事件名、续传编号；剩下的是 JSON schema 的活。

有问题的是 `EventSource`：

| 缺陷 | 后果 |
|---|---|
| `onerror` 里拿不到状态码和响应体 | 401 过期、500 崩了、CORS 配错、断网，在前端**长得一模一样** |
| 发不了自定义请求头 | 带不了 `traceparent`——**客户端的失败物理上无法和服务端日志对上号** |
| 只能 GET | 参数进 URL，prompt 明文躺进 access log 和浏览器历史 |
| 重连节奏不可控 | 没有退避没有抖动，服务端一恢复所有客户端齐射；也分不清「该重试」和「重试也没用」 |

换成 `fetch` + `ReadableStream` 之后这些全部拿回来了，代价是分帧和重连要自己写。**而这个项目的代价特别低**，因为续传的重活本来就全在服务端（`record.events` 的数组下标就是 id），客户端只需要把上次的 id 放进请求头——EventSource 白送的两样，这里本来只用得上一半。

换完之后有一处**从判死变成了自愈**：心跳超时。以前连接看着是开的、一个字节都不来，浏览器不认为需要重连，撞上阈值只能放弃；现在撞上就主动 abort 并重连，靠 `Last-Event-ID` 无缝续上。**同一个阈值，含义完全不同。**

顺带踩到一个 CORS 坑：`traceparent` 和 `Last-Event-ID` **都不在安全清单里**，不在 `Access-Control-Allow-Headers` 里显式放行，浏览器会在预检阶段静默剥掉——不报错，表现是「排障编号莫名其妙对不上」「重连总是从头补」。

**排障能力的三件事，做完之后回头看，有一件我原本的设计是错的。**

**一、失败分类。** 原来 `record.error` 只有一句人话，它同时要服务三种读者而三种都没服务好：用户看不出是谁的问题、界面没法决定给不给重试、排障的人只能 grep 一句随时会被改掉的中文。拆成 `code` / `message` / `retriable` 三个字段，其中 `retriable` 是**唯一直接决定界面行为**的那个——为真才给重试入口。**给一个必然再次失败的操作配重试按钮，是把无能为力包装成了选择。**

关键在于分类**在抛出的地方就打好**，而不是事后拿正则去匹配错误文案。后者是最脆的做法：改一句提示语分类就静默失效，且没有任何测试会因此变红。只有两种线索例外，因为它们比我们自己的判断更可信——`AbortSignal.timeout()` 抛的 `TimeoutError` 和子进程的 `ETIMEDOUT`，那都是**平台定义的名字**。

**二、结构化日志。** trace-id 之前已经能生成、能回传、能显示给用户了——但用户报了编号过来，**服务端日志里搜不到它**。桥两头都搭好了，中间没铺板。所以每条日志都必须带 `traceId`：不带它的日志在排障时约等于不存在。日志**写 stderr 而不是 stdout**，因为在这个项目里 stdout 是协议通道（见 21 节），而且这样 `pnpm analyze > report.txt` 也不会把日志混进产物。

**三、独立的 `error` 事件——这条我推翻了自己。** 我原本打算把终态错误从 `done` 里拆出来单发一个 `error` 事件。写之前重新想了一遍：那会造成**两条终止路径**，客户端要处理两种结束方式，而它们表达的是同一件事。`done` 带一个结构化的 `failure` 字段已经够了，**一个终态事件、一个状态字段**比两个事件更简单。真正需要独立错误事件的是**非终态的错误**（某次工具调用失败但流程继续），而那个早就有了——`emit({phase: "error"})` 的进度事件。

**但换传输层只是解开枷锁，不是成果。** 真正的排障能力是另外四件事：每个任务一个贯穿客户端与服务端的编号、错误分类（可重试 / 致命）、独立的错误事件、以及**把编号显示在界面上让用户报得出来**。前两件用 EventSource 做不了，后两件做得了、只是以前没做。编号用 W3C Trace Context 的 `traceparent`：这个单进程工具其实只用得上里面的 trace-id，span 树是摆设——**按标准来是因为成本十几行，而自造格式将来接 APM 一定要改**。

**后台任务是离线的，这条得当不变量守，不能当「顺便也支持」。** 用户发起一次分析之后可以断网、可以关页面、可以换设备，**只有显式 cancel 才该终止它**——要求用户盯着页面等几分钟本身就是设计错误。

这条承诺真正的薄弱点不在业务逻辑里，而在**唯一一处「客户端的问题」能物理接触到服务端**的地方：那条 SSE 流。Node 流上没有 `error` 监听就是未捕获异常，而 Koa 的 respond 是 `body.pipe(res)`（`application.js:303`），**`pipe()` 不会给源流挂 error 监听**，`onFinished` 听的也是 response 不是它。所以只要有谁 `destroy(err)` 了那条流（socket hang up、代理掐断），整个进程就没了——**不是「这个订阅者掉线」，是所有人的任务一起陪葬**。

补上的是一行空监听，故意什么都不做：订阅者的链路出问题不是任务的故障，不该改状态、不该记 error、更不该往上抛。这和工具事件回填那条是同一句话——**观察者的失败不能改变被观察者的行为**。

同一组不变量还包括：淘汰只挑已完成的任务（`evictOld` 里那个 `status !== "running"` 过滤，关页面几分钟后回来记录还得在），以及所有订阅者走光也不触发任何终止逻辑。这些现在都有用例守着，因为它们之前**只是碰巧成立**。

**心跳定时器有两段各自独立的生命周期问题，两段都是跑起来才撞出来的。**

一段是**结束之后**：`clearInterval` 挂在 `close` 上，而 `finish()` 调的 `stream.end()` 只结束**可写端**——`close` 要等读端也消费完才来。没人读这条流的时候这段空隙可以无限长，心跳每一次触发都是 `ERR_STREAM_WRITE_AFTER_END`，流上没人听 `error` 就是未捕获错误，**直接崩进程**。所以心跳里加了一道 `writableEnded || destroyed` 的守卫。

另一段是**结束之前**：`setInterval` 默认 ref 住事件循环，一条挂着心跳的流足以让整个进程无法自然退出（实测去掉 `unref` 后进程挂死，只能被强杀）。`unref()` 表达的是「这个定时器没有让进程继续跑的资格」——它只是给活着的连接保活，不是活着的理由。两者覆盖的时间段不相交，缺一个都不行。

**顺带修掉一个说过头的说法。** 「`AbortController` 一路传到 `streamText`」只对 `ask` 成立：`narrate` / `propose` / `workflow` 里一个 signal 都没有，所以 analyze 模式下点停止，界面停了、状态写成 `cancelled` 了，而那次 18 秒的模型调用照样跑完、token 照烧。LangGraph 自己能在**节点边界**中止，但那救不了正在飞的请求——signal 必须一路递到发请求的地方。

## 19. 布局错位只有跑起来才看得见

两个界面 bug 都属于「代码读一百遍也发现不了」的类型：

- `.panel-head` 这个类在 CSS 里**根本不存在**（样式表里定义的是 `.panel-heading`），于是标题和内容全部贴着边框
- `.timeline-row` 是 `grid-template-columns: 18px 1fr auto` 的三列网格，而追问面板只给了两个子元素，名字落进 18px 那一列——中文被压成一列竖排

类型系统对 `className` 字符串一无所知，测试也不会去断言视觉。这类问题的唯一解法就是**真的把界面跑起来看一眼**。这和项目里另一条经验是同一件事：三次「代码写完了但从没运行过」的事故，都是靠端到端跑一遍才发现的。

## 20. 同一套工具，两个协议出口

`ask` 与 MCP Server 面向的是两拨模型：前者是我们自己编排的循环，后者是别人的编辑器。但它们用的**必须是同一份工具实现**。

所以 `mcp.ts` 不重新定义工具，而是从 `tools.ts` 的 tool 对象上取 `description` 与 zod schema，转成 MCP 的注册格式：

```ts
server.registerTool(name, {
  description: definition.description,
  inputSchema: definition.parameters.shape,   // ZodObject → ZodRawShape
  annotations: { readOnlyHint: true, openWorldHint: false },
}, handler)
```

复制一份会怎样很容易预见：某天在 `ask` 这边修了「路径写错时给候选」，MCP 那边还在返回 not found。**两个出口给出不同的事实，比少一个出口糟糕得多**——这和前后端字段契约那条是同一个道理。

顺带的好处是 `readOnlyHint` 可以如实声明：九个工具确实一个都不写盘，客户端据此决定要不要弹确认框。改造能力**没有**接进 MCP，因为那是会写盘的操作，不该藏在一个标着只读的协议出口后面。

## 21. stdout 是协议通道

接 stdio transport 最容易踩的坑：项目里 `graph.ts` 会打印 alias 解析统计、`storage.ts` 会打印原生模块降级告警——任何一行 `console.log` 混进 stdout，客户端解析 JSON-RPC 就会失败，而且报错完全看不出根因。

所以建立传输之前先把 `console.log` / `info` / `warn` 改道到 stderr。日志不丢，只是换条道走。

这条也决定了测试怎么写：MCP 的测试**故意挑了会打印 alias 日志的 fixture**（`11-vite-alias`）。如果重定向失效，握手就直接失败——**能连上本身就是一条断言**，比事后 grep stdout 可靠得多。
