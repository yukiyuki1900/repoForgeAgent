# 已知限制

诚实列出，避免误判能力边界。

## 性能与资源

| 限制 | 说明 |
|---|---|
| 全量解析，无增量 | `scanner.ts` 已计算 `contentHash`，但尚未用于跳过未变更文件 |
| 模块解析无缓存 | 每个 import 都走一次 `ts.resolveModuleName`，未传 `ModuleResolutionCache`，大仓上是主要耗时来源 |
| ts-morph Project 不释放 | 全量保留 AST，万级文件仓库的内存占用需要实测 |
| `runs` 表只增不删 | 每次分析插入一份完整报告 JSON，`.reposurgeon/index.db` 会随运行次数膨胀 |

## 解析覆盖面

| 限制 | 说明 |
|---|---|
| 单仓 tsconfig | 只读取仓库根目录的 tsconfig；monorepo 子包各自的 `paths` 尚未逐包解析 |
| alias 只做静态提取 | 支持对象字面量、数组形式、简写属性与同文件内变量引用；若 alias 由插件动态注入或定义在被 `import` 的独立文件里则读不到，此时会打印告警 |
| 无调用边 / Hook 使用边 | 当前只有 import 与 render 两类关系 |
| 架构分层按目录名推断 | 模块划分会先剥离公共前缀（如 `src/`）再聚合，但分层判定仍以目录名为准，尚未结合依赖方向 |

## 执行计划

| 限制 | 说明 |
|---|---|
| 意图识别是关键词规则 | 覆盖依赖 / 架构 / 质量 / 检索四类，长尾表达会落到「检索」这个兜底分支；判错时用 `--full` 跑满 |
| 裁剪粒度是节点，不是数据 | 只能决定某个分析器跑不跑，不能决定「只分析 src/pages 这个子树」 |
| 不按仓库规模自适应 | 万级文件仓库仍会全量 `parseSemantic`，尚未按规模收紧上下文预算或降级为抽样 |
| `dependency` / `quality` 不可裁剪 | 它们的产出是报告必填项，属于有意为之而非疏漏 |

## 改造（`refactor --apply`）

| 限制 | 说明 |
|---|---|
| 只做 `import type` 一种变换 | 提取共享模块、依赖倒置这类修复是架构决策，需要模型生成代码，无法用编译器证明行为不变，故不在自动化范围内 |
| 不写入 `.vue` | SFC 的 script 块被抽成虚拟 TS 文件，行号与源文件不对齐；判定结果照常给出，标注为「需人工修改」 |
| 混用内联 `type` 修饰符的导入不改 | `import { type A }` 要先清掉修饰符才能升成声明级 `import type`，否则产出非法语法 |
| 要求目标文件已被 git 跟踪且干净 | 回滚依赖 `git checkout --`；未跟踪或有未提交改动时直接拒绝，不做自建快照 |
| 类型验证是全量 pre-emit 检查 | 大仓上单次数十秒，且改造前后各跑一次；尚未按受影响文件裁剪 |
| 结构验证会整仓重扫 | 写入后重新扫描、重建依赖图、重跑 Tarjan，成本约等于一次完整分析 |

## 未使用的导出（`analyzeDeadExports`）

判定一律从严：**宁可漏报，不能误删**。下面每一条都是刻意选择的漏报，不是没想到。

| 限制 | 说明 |
|---|---|
| 默认导出整体不判定 | `export default` 没有稳定的名字可供引用分析，真实引用又大多来自路由表、`lazy(() => import(...))` 这类动态位置，静态判定必然误报 |
| 动态引用检测不到 | 字符串拼接的 `import(\`./\${name}\`)`、运行时反射、依赖注入容器按名字取值，这些引用在 AST 上不存在 |
| `.vue` 文件跳过 | SFC 抽成虚拟 TS 文件后，模板与路由里的组件引用全部丢失，逐个判定只会产生误报 |
| 被 `export ... from` 转发的符号一律排除 | 不追踪转发链末端——那需要先判定 barrel 文件本身是否被消费 |
| 框架约定名单不可能全 | `getServerSideProps` 这类由框架按字符串查找的导出靠白名单排除；名单漏一个只会少报一条，属于可接受方向 |
| 入口识别是启发式 | 读 `package.json` 的 `main`/`module`/`exports`/`bin` 加约定文件名；`dist/x.js` 按同名源码回推一次，非常规构建产物路径会漏 |
| 解构导出不收集 | `export const { a, b } = obj` 删掉单个绑定会改变解构语义，超出安全改法范围 |
| 每个符号一次引用分析 | 未做批量优化，导出数量很多的大仓会明显变慢 |

## 死导出清理（`applyDeadExportRemoval`）

只做两种改法：**去掉 `export` 关键字**（声明还在，语义等价）和**删除整条声明**。
路线图里的第三种「删除整个文件」不做——那需要判断文件整体是否还有存在意义，属于人的决策。

| 限制 | 说明 |
|---|---|
| 清理有级联，一轮不收敛 | 删掉 A 之后，只被 A 用过的 B 才变成真正的死代码。一次运行只保证**这一轮**的判定正确，需要反复运行到没有新改动为止 |
| 所有导出都死的文件整个不动 | 全部移除后文件不再含任何 `import`/`export`，就不再是 ES module，顶层声明会落进全局作用域。这种文件多半整个都该删，交给人 |
| 初始化有副作用的变量不删 | 用白名单判断表达式是否纯：字面量、函数、数组/对象字面量算安全，函数调用、`new`、属性访问（可能触发 getter）一律拒绝 |
| 带装饰器的类不删 | 装饰器在求值时执行，删除会改变运行时行为 |
| `export const a = 1, b = 2` 不做 unexport | 去掉 `export` 会连带影响同一条语句里的其它绑定 |
| 结构验证是整仓重扫 | 写入后重新扫描、重新收集全部导出，成本约等于一次完整分析 |

## 交互式追问（`ask`）

| 限制 | 说明 |
|---|---|
| 强制需要模型 | 与分析不同，`ask` 没有降级路径——「自己决定查什么」无法由规则替代 |
| 每次都重建索引 | 一次提问要完整扫描 + 解析一遍仓库，319 文件约 5 秒；尚未复用 `analyze` 写下的索引 |
| 不记上下文 | 每次 `ask` 都是独立的，不能基于上一次的结论追问 |
| 流式文本只在内存里 | 断线重连能补齐已生成的部分，但服务重启后就没了；任务本身也只保留最近 20 个 |
| 回答不可复现 | 同一个问题两次提问的工具调用路径可能不同。工具层与循环控制有回归测试，回答本身依赖人工核对——答案强制带路径行号正是为此 |

## MCP Server

| 限制 | 说明 |
|---|---|
| 一个进程绑定一个仓库 | 路径在启动参数里定死；要分析多个仓库就配多个 server 条目 |
| 索引不自动失效 | 惰性构建后一直缓存，改完代码需要显式调 `refreshIndex`；尚未按文件 mtime 自动检测 |
| 只暴露只读工具 | 改造能力刻意没有接入——写盘操作不该藏在一个标着 `readOnlyHint` 的协议出口后面 |
| 仅 stdio 传输 | 没有实现 SSE / HTTP transport，因此只能本机使用 |

## Skill

| 限制 | 说明 |
|---|---|
| Windows 上符号链接会退化 | 客户端目录是指向 `.agents/` 的符号链接；Windows clone 需要 `core.symlinks=true` 且有相应权限，否则会变成内容为路径字符串的普通文件，Skill 静默不加载 |
| 装在项目级只对本仓库生效 | 要在被分析的项目里用，需按 README 链到 `~/.claude/skills/` 或 `~/.cursor/skills/` |
| 只挂 MCP 时第 4 步不完整 | 「这条边能否改成 `import type`」依赖 refactor 的引用分析，没有暴露成 MCP 工具；手册里已标注此时应如实说明查不了，而不是读源码猜 |
| 手册内容不参与类型检查 | `tests/skill.test.ts` 能验证工具名、命令名、文档路径与链接完整性，但判断标准写得对不对仍然只能靠人读 |

## 检索与恢复

| 限制 | 说明 |
|---|---|
| 检索未接入 FTS5 与向量 | SQLite 建了 `files_fts` 表但主流程用的是关键词匹配；中文长尾表达依赖 LLM 查询计划 |
| checkpoint 不支持恢复 | 状态快照写入了 SQLite，但没有基于它的 resume 逻辑；LangGraph 侧用的是进程内 `MemorySaver` |

## 交互

| 限制 | 说明 |
|---|---|
| 目录反查依赖同机后端 | 浏览器不给绝对路径，只能靠后端按目录特征搜索；搜索范围限定在 cwd 周边与 home 目录 |
| 原生目录选择器兼容性 | `showDirectoryPicker` 仅 Chrome / Edge 支持，其它浏览器自动回退到服务端目录浏览器 |
| 前端构建产物需要 API 地址配置 | 相对路径 `/analysis` 依赖 vite dev proxy，静态托管 `web/dist` 时无法访问 API |

## 路线图

1. **增量索引** — 用 `contentHash` 跳过未变更文件，把大仓重复分析的成本降下来
2. **大仓性能基线** — 在万级文件真实仓库上测出解析耗时曲线
3. **关系边扩展** — 函数调用边、Hook 使用边、Store 使用边
4. **分层推断结合依赖方向**，而不只看目录名
5. **改造验证接入测试** — 目前的判据是「不新增类型错误」+「环数 / 导出数与预测一致」，还缺一环：跑目标仓库自己的测试。这一步要执行目标项目的脚本，需要先有沙箱隔离
6. **AI 提方案** — 让模型处理「工具主动放弃的那部分」（检出了但不敢动的、被规则排除的、只被测试引用的），输出结构化指令加可证伪的预测。边界设计已定稿见 [PROPOSAL.md](PROPOSAL.md)，尚未实现。**这条链路不会提供全自动执行**——它改的正是工具判定为不安全的东西
7. **`ask` 复用已有索引** — 目前每次提问都重扫一遍仓库，应当读取 `analyze` 落下的结果
8. **多轮追问** — 保留上一次的工具调用结果与结论，支持在同一个会话里继续问
