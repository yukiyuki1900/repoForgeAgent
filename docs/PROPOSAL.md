# AI 提方案：边界设计

> 这份文档在写代码之前定稿。它约束的不是「能做什么」，而是**不能做什么**——
> 这个功能最大的风险不是做不出来，是做成装饰：模型输出一段听起来有道理的话，
> 人看了点头，但它没有被任何东西约束。

## 一、模型站在哪一层

前两条改造链路（`import type` 破环、死导出清理）里模型的参与度是**零**。它们是纯确定性的：规则判定、机械改写、编译器验证。

这不是缺陷，是有意为之——能算出来的绝不问模型。但它也划出了一条清晰的空白地带：

```
死导出跑完后，候选被分成四堆：

  edits      机械上安全      →  工具已自动处理            ← 模型无事可做
  blocked    检出了但不敢动  ┐
  testOnly   只被测试引用    ├─  规则明确放弃的部分        ← 模型的战场
  excluded   被规则排除      ┘
```

拆环那边同构：`refactor.ts` 有七种「不可改原因」，那些边同样落在这个地带。

**所以模型的任务不是「重新判断一遍工具已经判断过的事」——那是装饰。它处理的是规则主动放弃的部分。**

一句话定位：

> 工具处理机械安全的部分，模型处理剩下的部分，
> 但模型的每一个方案都必须带一个**可证伪的预测**。

### 候选池实测

在写代码前先量了一下这块地带到底有多大——拿现有两个 fixture 跑 A1/A2：

| fixture | 工具自动处理 | **模型的候选池** |
|---|---|---|
| `18-dead-exports` | **0** | **11**（4 blocked + 1 testOnly + 6 excluded） |
| `19-dead-export-removal` | 3 | 2（1 blocked + 1 excluded） |

`18-dead-exports` 那一行是关键：**纯规则一个都处理不了，11 个候选全部落在模型这边。**

而且三种 kind 在现有 fixture 上都有真实对应，不是设计出来的假想场景：

```
delete-file                src/dead.ts     两个导出全死、入边为 0、顶层无副作用
delete-with-dependencies   src/effects.ts  registered = register()，初始化有副作用
unexport-symbol            src/lib.ts      publicApi 被判「入口导出即对外 API」
```

这一步花了十分钟，但它回答了「这个功能有没有用武之地」——**先量再做，避免做完才发现候选池是空的。**

## 二、模型看得到什么

`src/facts.ts` 负责把事实打包。对每个候选提供：

| 字段 | 为什么需要 |
|---|---|
| `file` / `symbol` / `line` / `kind` | 定位 |
| **`declarationText`** | 判断的主要依据。不给源码，模型只能靠名字猜 |
| **`whyToolRefused`** | 工具放弃的确切原因，模型要针对它论证 |
| `internalReferences` | 文件内哪几处在用它，决定能不能整条删 |
| `fileInboundCount` | 这个文件被几个文件 import。为 0 是删整文件的前提 |
| `siblingExports` | 同文件其它导出的存活情况 |

### 规模控制

候选可能有几十个，每个都带源码。硬上限：

- 单个符号的 `declarationText` **最多 40 行**，超出截断并标注
- 候选总数**最多 30 个**，按「最可能可处理」排序后截断
- 总预算约 **12k token**，复用 `narrate` 已有的 `estimateContextTokens` 估算

**截断必须写进上下文。** 静默截断会让模型把「前 30 条」当成全部，然后给出一个自信的错误结论——这条教训在工具层已经踩过一次。

### 实现状态

`src/facts.ts` 已完成（C1）。实测 `18-dead-exports` 的 11 个候选渲染后约 **985 token**，离预算很远——上限主要是给大仓准备的。

上下文用 Markdown 而不是 JSON：同样的信息，JSON 里源码要整段转义，换行变 `\n`、引号变 `\"`，既占 token 又难读。

候选排序决定了「被砍掉的是哪些」，依据只用确定性事实：整个文件死透的最前（入边为 0、导出全死、顶层无副作用），入口文件的导出最后——它们最可能真的是对外 API。

## 二点五、schema 的两个实现决定（C2）

`src/propose.ts` 已完成。

**operation 用扁平结构，不用 discriminated union。** 结构化输出对嵌套 union 的支持在各家网关上表现不一，而这里真正需要 schema 保证的只有「字段类型对」。**哪些字段组合合法是语义问题，交给 C3**——那一层能查符号是否真的存在，schema 查不了。

**候选池为空时不发起调用。** 面对空清单模型只会编，白花一次调用还引入幻觉风险。

## 三、模型能提哪几种方案

**枚举，不允许自由发挥。** 三种，按风险从低到高：

### 1. `delete-file` —— 删除整个文件

**场景**：一个文件的所有导出都死了。A2 会把这种情况整体 blocked（移除后文件不再含任何 `import`/`export`，就不再是 ES module），理由是「这种文件多半整个都该删，交给人」。模型就是来做这个判断的。

```ts
{ op: "delete-file", path: string }
```

**硬前置**（由 C3 校验，不信模型的话）：

- 文件入边数为 0——没有任何文件 import 它
- 文件顶层没有副作用语句（非声明语句、IIFE、立即执行的赋值）
- 文件的全部具名导出都在死导出清单里

**预测**：`{ exportsRemoved: n, filesRemoved: 1 }`

### 2. `unexport-symbol` —— 降级一个被规则排除的导出

**场景**：`excluded` 里那些。比如一个位于 `src/index.ts` 的导出，规则一律认为「入口导出即对外 API」，但这个包根本没发布，或者模型读过之后确认它是历史遗留。

```ts
{ op: "unexport", file: string, symbol: string }
// 或
{ op: "delete-declaration", file: string, symbol: string }
```

**硬前置**：

- 符号确实在 A1 的 `excluded` 或 `testOnly` 清单里（不接受模型自己发现的"死导出"）
- 选 `delete-declaration` 时，初始化表达式必须通过 `isPureExpression`——**这条不因为模型说安全就放行**

**预测**：`{ exportsRemoved: 1 }`

### 3. `delete-with-dependencies` —— 连带删除私有依赖

**场景**：`export const registered = register()`。A2 拒绝它，因为初始化是函数调用、删掉就少执行一次 `register()`。模型读过 `register` 之后可能判断：它只是往一个从没被读过的变量里写，删掉没有实际影响。

```ts
[
  { op: "delete-declaration", file, symbol: "registered" },
  { op: "delete-declaration", file, symbol: "register" }   // 连带
]
```

**硬前置**：

- 每个被连带删除的符号，全仓引用数必须**恰好为 1**（就是要删的那一处）
- 连带符号必须是非导出的私有声明

**预测**：`{ exportsRemoved: 1 }`

> ⚠️ **这是三种里唯一一种不保证行为等价的。**
>
> 「这个副作用不重要」无法用编译器证明。工具能保证的只有「改动是机械正确的、导出数对得上」，**保证不了运行时行为不变**。
>
> 因此这一类：风险等级强制为 `high`、必须人工确认、且要在界面上明写这句话。
> 主动说出边界，比被问出来强得多。

## 四、明确不做的事

比「能做什么」更重要。

| 不做 | 为什么 |
|---|---|
| **模型生成代码文本** | 只输出结构化 operation，由 ts-morph 机械执行，语法由编译器保证 |
| **没有数字预测的方案** | **在 schema 层面就无法表达**。`exportsRemoved` 是 `z.number().int().positive()`——不是提示词里的一句请求，是结构约束。一个不能被证伪的方案，和一段客套话没有区别 |
| **跨文件搬运符号**（`move-symbol`） | 要判断「正确的层」，属于架构决策；且现有对账指标覆盖不到它 |
| **修改函数体** | 完全不碰。改行为的事不在这个功能的范围内 |
| **全自动执行**（`--apply`） | 见下一节 |
| **自然语言的「重构建议」** | 那是 `ask` 的活。这里只产出可执行、可对账的方案 |
| **模型自己发现的死导出** | 候选只能来自 A1 的检测结果。模型说「我觉得这个也没人用」一律不采信 |

## 五、为什么不提供 `--apply`

前两条链路都提供了 `--apply`，这条不提供。区别很清楚：

```
import type 破环   语义等价的机械变换          →  可以全自动
死导出的机械部分   规则判定安全 + 双层验证      →  可以全自动
模型提的方案       改的正是「工具判定不安全」的东西  →  不能全自动
```

工具主动放弃了那些判断，模型接手之后不能因为「模型说可以」就把它们变回自动。**人必须在执行前看到方案、预测和风险等级。**

交互形态：列出方案 → 人选中一条 → 执行这一条 → 双层验证 → 不符回滚。
**不提供「全部执行」按钮。**

## 六、静态校验（C3）：幻觉的主要防线

模型输出之后、给人看之前，逐条核对。**模型编一个不存在的符号名是常态，不是异常。**

`src/validate.ts` 已完成。核心立场：**不采信模型说的任何一个事实**——符号存不存在、引用有几处、文件有没有人 import，全部对着 AST 重新查一遍。模型贡献的只有「该不该动、怎么动」这个判断。

| 检查 | 不通过的处理 |
|---|---|
| 候选来自 A1 的清单，不是模型自己发现的 | 丢弃 |
| `operations` 的组成与 `kind` 相符 | 丢弃 |
| 每条 operation 的文件在本次扫描结果里 | 丢弃 |
| 每条 operation 的符号真实存在 | 丢弃 |
| 两个方案没有碰同一个符号 | 丢弃后一个 |
| `prediction` **等于**静态推算出的期望值 | 丢弃 |
| `delete-file`：入边为 0、顶层无副作用、导出全死 | 丢弃 |
| `unexport-symbol` 走 `delete-declaration` 时：初始化表达式纯 | 丢弃 |
| `delete-with-dependencies`：连带符号非导出、引用数恰为 1、**且那一处就在目标声明内部** | 丢弃 |
| `delete-with-dependencies` 的风险等级为 `high` | 强制改写为 `high`，留痕 |

被丢弃的方案**记录原因并可查**，但不进入给人看的列表。理由和 `excluded` 一样：判据可以被质疑，但不能是隐形的。

### 关于 `prediction` 的一个反直觉设计

确定性代码其实**能自己算出** `exportsRemoved` 应该是多少。那还要模型预测干什么？

因为预测的用途不是告诉我们答案，而是**检测模型有没有真正理解自己提的方案**。算出来的期望值和模型的预测不一致，说明它对自己那几条 operation 会产生什么效果判断错了——这种方案哪怕碰巧能执行成功，也不该采纳。

于是形成两道对账，防的是两件不同的事：

```
C3（校验时）  模型预测   vs  静态计算的期望值   →  模型理解偏差
C4（执行后）  静态计算   vs  重扫仓库的实测值   →  执行偏差
```

### 写测试时改掉的两条规则

**纯度判据不能套在 `delete-with-dependencies` 上。** 初版对所有 `delete-declaration` 都要求初始化表达式纯，结果 `export const registered = register()` 被自己拦下了——而那**正是**这个 kind 存在的唯一理由。这一类的目标按定义就是不纯的，它换来的是强制 `high` + 人工确认，不是纯度检查。

**「引用数恰为 1」单独一条不够。** 一个在别处被用了一次的私有符号同样能凑出 1。补成：那唯一一处必须落在**目标声明的字符区间内**，删掉目标之后它才真的没人用。

## 七、执行与对账（C4）

`src/execute.ts` 已完成。验证骨架整个复用 `verify.ts`，改写原语（`unexport` / `remove`）从 `prune.ts` 导出复用——**改写动作只有一份实现**，否则两条链路的行为迟早会分叉，而分叉的那一刻两边的验证都还是绿的。

```
第一层  类型不新增错误                        （verify.ts 已有）
第二层  实测导出数 == before - exportsRemoved
        实测删除文件数 == filesRemoved
不符    git checkout 整体回滚                 （verify.ts 已有）
```

**两个数字各自对账。** 合成一个判据的话，「删对了几个导出」就能掩盖「删错了几个文件」。

判据仍然是「完全相等」而不是「变少了」——后者只要删掉任何一个导出就成立，等于没验证。

### 端到端用例挖出的一个洞

初版对 `delete-file` 的处理是 `project.removeSourceFile()`，想让类型检查如实反映「这个文件没了」。**那是无效的**：Project 建在真实文件系统上，从项目里移掉之后 TypeScript 仍会顺着 `import` 从磁盘把它读回来当依赖。结果是删一个正被 import 的文件也能一路绿灯通过类型检查——**第一层验证对这类改动等于没开**。

改成在内存里把它替换为 `export {};`，让类型检查回答「还有人在用这个文件的导出吗」。

已知缺口如实记在代码里：`import "./config"` 这种纯副作用导入，换成空模块不会报错，只有文件真的消失才会。这一类由 `isWholeFileDead` 的入边检查兜底。

### 变异测试挖出的一个死条件

判据里原本还有一条 `survived.length === 0`（说好要删的文件是不是真的不在了）。变异测试给它判了 **0/8**——不是断言漏了，是**这个条件在逻辑上永远不会独立触发**：`actual = deleted.length - survived.length`，只要 `predicted` 是对的，`survived` 一非空就必然让文件数那条等式先不成立。

删掉了。**一个永远由别人代劳的判据，留着只会让防线看起来比实际更厚。** 但 `survived` 这个列表进报告——它说得出是哪个文件没删掉。

## 七点五、交互（C5）

`src/proposalflow.ts` 把三段串起来：收集事实 → 模型提 → 静态校验 → **交给人看，到此为止**。

编排本身只有二十来行，值得单列一个文件的理由是它划出了自动化的终点：这个函数返回方案列表就结束了，不会顺手执行任何一条。

```bash
# 列出方案（不写任何文件）
reposurgeon refactor <dir> --propose

# 人挑一条，执行这一条
reposurgeon refactor <dir> --propose --execute 2
```

`--execute` **刻意只接受单个序号**。没有「全部执行」，而且这句话直接印在输出里——不提供它是设计，不是没来得及做。

被拦下的方案和被强制改写的字段也一并列出。理由和 `excluded` 一样：**判据可以被质疑，但不能是隐形的。** 一个只展示成功结果的工具，没法让人判断它靠不靠谱。

## 八、怎么测一个依赖模型的功能

**桩模型测控制流，不测回答质量。** 和 `tests/tools.test.ts` 里测 agent loop 用的是同一套办法。

四层各测各的，`tests/proposalflow.test.ts` 测它们串起来之后是否还成立：

| 桩模型返回 | 期望行为 | 在哪测 |
|---|---|---|
| 没有 `prediction` 的方案 | schema 层就拒绝 | `propose.test.ts` |
| 一个不存在的符号名 | C3 拦下，方案不进入列表，但原因可查 | `validate.test.ts` / `proposalflow.test.ts` |
| 预测数字与静态推算不符 | C3 拦下 | 同上 |
| 预测数字与实测不符 | 执行后对账失败，磁盘还原到改动前 | `execute.test.ts` |
| `risk: low` 的连带删除 | 强制改写为 `high` 并留痕 | `validate.test.ts` / `proposalflow.test.ts` |
| 空方案列表 | 不崩溃，如实说 | `proposalflow.test.ts` |
| 候选池为空 | **一次模型调用都不发起** | `proposalflow.test.ts` |

真实模型的方案质量不在这里测——那需要 key，且不可复现。但**「幻觉会不会被拦下」和「预测不符会不会回滚」这两件事必须能回归**，它们才是这个功能可信的全部理由。

执行层的用例刻意**绕过 C3** 直接把方案喂给执行器，包括几条 C3 本来就会拦下的。那不是在测无效输入，是在证明两层是独立的防线——**一条只在上游正确时才成立的防线，不叫防线。**

## 九、面试话术

> 前两条改造链路模型参与度是零，因为那些判断确定性代码能做。做到第三条时我把模型放在了一个特定位置：**工具主动放弃的那部分**——检出了但不敢动的、被规则排除的、只被测试引用的。
>
> 模型不输出代码，输出的是结构化指令加一个**可证伪的预测**：改完之后应该少几个导出。执行由 ts-morph 机械完成，然后用确定性代码重扫仓库对账，对不上整体 `git checkout` 回滚。
>
> 而且它输出之后、给人看之前还有一道静态校验：符号是否真的存在、候选是不是来自检测结果、连带删除的符号引用数是不是真的只有 1。模型编一个不存在的符号名是常态，不是异常。
>
> 这条链路我**没有**提供全自动执行。前两条有，因为那是语义等价的机械变换；这条改的正是工具判定为不安全的东西，人必须先看到方案和风险等级。

**如果被追问「你怎么保证行为不变」**——不要辩护，直接承认：

> 保证不了。类型检查加导出数对账能证明改动是机械正确的，证明不了运行时行为等价。特别是连带删除那一类，「这个副作用不重要」本来就不是编译器能判定的事。所以那一类风险等级强制为 high、必须人工确认，我也把这句话直接写在界面上。
