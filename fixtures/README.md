# Fixture 回归评估

把分析器当成一个 CLI 程序来测：不看模型说了什么，只校验它在固定输入上产出的**事实**——依赖环、组件清单、关系边。这样每一条能力都是可回归、可量化的。

## 运行

```bash
pnpm eval
```

## 用例结构

```
fixtures/<序号>-<用例名>/
├── expected.json     # 期望与状态声明
└── src/              # 一个最小化的仓库
```

`expected.json`：

| 字段 | 说明 |
|---|---|
| `title` | 用例标题 |
| `status` | `expected-pass`：当前必须通过；`known-failure`：当前已知做不到 |
| `why` | 为什么现在做不到——写清楚失败的根因，而不是笼统的「未实现」 |
| `requires` | 该用例依赖的可选包；缺失时标记为 `SKIPPED` 而不是判为回归 |
| `expect.cycles` | 期望检出的循环依赖，每项是构成环的文件路径集合（比较时忽略顺序） |
| `expect.cycleCount` | 环的**总数**。用来断言「不该有环」——只写 `cycles: []` 等于零条断言 |
| `expect.components` | 期望被识别为 `component` 的符号名 |
| `expect.edges` | 期望存在的关系边 `{ from, to, kind }` |
| `expect.metrics` | 维护性指标：`score` 总分、`dimensionCount` 参与评分的维度数 |
| `expect.refactor` | 改造计划：`candidates` 可拆边（数量必须精确匹配）、`blocked` 不可拆边及原因、`cyclesAfter` 改造后剩余环数 |
| `expect.deadExports` | 未使用的导出：`deadCount` 总数精确匹配、`dead` 必须检出的项、`testOnly` 仅测试引用、**`notDead` 绝不能出现在结果里的符号** |
| `expect.architecture` | 架构聚合：`sourceRoot` 剥离出的公共前缀、`modules` 必须聚出的模块、`minMermaidLines` 图的最小行数 |
| `expect.narration` | 送给 LLM 前的上下文摘要：`maxEstimatedTokens` 规模上限、`modules` 必须保留的模块聚合、`cycleCuts` 环上建议切点 |

## 五种结果

| 结果 | 含义 | 是否阻塞 |
|---|---|---|
| `PASS` | `expected-pass` 用例通过 | — |
| `KNOWN-FAIL` | `known-failure` 用例仍然失败，符合当前预期 | 否 |
| `REGRESSION` | `expected-pass` 用例挂了，能力出现回退 | **是**，退出码 1 |
| `FIXED` | `known-failure` 用例开始通过，需把 `status` 改为 `expected-pass` | 否，但会提示 |
| `SKIPPED` | `requires` 声明的可选依赖没装，用例未执行 | 否 |

这样设计的目的：**已知的短板不会污染红绿信号，但也不会被悄悄忘掉。** 每次补齐一项能力，就有一个用例从 `KNOWN-FAIL` 变成 `FIXED`，通过率的变化即是能力提升的证据。

## 变异测试：证明断言不是永远绿的

死导出这条链路上最重要的断言都是「**什么都没发生**」型的——某个符号绝不能出现在结果里、某个文件绝不能被改动。这类断言最容易写成摆设：实现里根本没跑到那段逻辑，它照样是绿的。

所以两层都做了变异：逐条破坏实现，看断言会不会红。

### 检测层（`18-dead-exports` 的 `notDead`）

| 变异 | 结果 |
|---|---|
| 关掉「入口文件」排除 | REGRESSION 14/18 |
| 关掉「框架约定名」排除 | REGRESSION 16/18 |
| 关掉「被 `export` 转发」排除 | REGRESSION 16/18 |
| 同文件引用误记为外部引用 | REGRESSION 15/17 |
| 原始实现 | PASS 18/18 |

**四个变异的失败条数各不相同**，说明每条排除规则都有独立断言覆盖，而不是一条在兜底。最后一个连断言总数都变了（18 → 17）——`buildUrl` 不再进入结果，挂在它上面的 `usedInFile` 子断言随之消失。

### 执行层（[tests/prune.test.ts](../tests/prune.test.ts)）

|---|---|
| `delete-declaration` 空转 | 失败 3/5 |
| `unexport` 变量分支空转 | 失败 3/5 |
| `unexport` 函数分支空转 | 失败 3/5 |

| 原始实现 | 失败 0/5 |

### 事实包（[tests/facts.test.ts](../tests/facts.test.ts)）

给模型的上下文本身不产生任何判断，但它决定了模型能不能做对判断。喂错了事实，后面的静态校验和对账再严也只是拦住一个本来就不该产生的方案。

| 变异 | 结果 |
|---|---|
| 静默截断（不报省略数） | 失败 2/7 |
| 不给声明源码 | 失败 2/7 |
| 候选排序失效 | 失败 2/7 |
| 不做候选数上限截断 | 失败 2/7 |
| 把工具已自动处理的也塞给模型 | 失败 4/7 |
| 原始实现 | 失败 0/7 |

第一条对应的是这套工具付过一次代价的教训：**静默截断会让模型把「前 30 条」当成全部**，然后给出「其余导出都还在用」这种自信的错误结论。`20-many-candidates` 就是为了让这条断言有东西可看——它的候选池是 34 个，正好越过上限。

### 提方案层（[tests/propose.test.ts](../tests/propose.test.ts)）

模型唯一参与决策的地方。桩模型测的是**约束**，不是回答质量——真实模型提的方案好不好需要 key 且不可复现，但「没有数字预测的方案能不能进来」必须能回归。

| 变异 | 结果 |
|---|---|
| `prediction` 允许为 0 | 失败 2/7 |
| `prediction` 整体改成可选 | 失败 2/7 |
| `kind` 从枚举放开成自由字符串 | 失败 1/7 |
| 候选池为空时也发起调用 | 失败 2/7 |
| 不把事实喂进 prompt | 失败 2/7 |
| 原始实现 | 失败 0/7 |

前两行验证的是同一件事：**「每个方案必须带可证伪的预测」这条约束落在 schema 上，不在提示词里。** 提示词写了什么不重要，模型能输出什么由 schema 决定。

### 静态校验层（[tests/validate.test.ts](../tests/validate.test.ts)）

幻觉的主要防线。**每一条拒绝规则都配一个对应的幻觉样本**——规则写了但没有样本，等于没人知道它到底会不会触发。

| 变异 | 结果 |

| 候选清单检查失效（模型自己"发现"的死导出也放行） | 失败 2/13 |
| `prediction` 对账永远成立 | 失败 1/13 |
| `delete-file` 前置检查关掉 | 失败 1/13 |
| 连带引用数不再要求为 1 | 失败 1/13 |
| 不检查唯一引用的位置 | 失败 1/13 |
| 允许导出符号作为连带依赖 | 失败 1/13 |
| `risk` 不再强制改写为 `high` | 失败 1/13 |
| 符号存在性检查关掉 | 失败 1/13 |

| 原始实现 | 失败 0/13 |

**第一轮跑「符号存在性检查关掉」是 0/11——又一次假绿。**

断言没写错，是那条路径根本没被走到：唯一一处编造的符号是 `targetSymbol`，而它在**第 1 关（候选清单）**就被拦下了，压根到不了第 3 关。`operations` 里的符号从头到尾都是真的。

补的两条用例才是更常见的幻觉形态——**目标从候选清单里挑对了，落到指令时把符号名拼错、把文件路径写错**。补完这条变异变成 1/13。

这和下面那个桩模型陷阱是同一个病根，只是换了张皮。

### 方案执行层（[tests/execute.test.ts](../tests/execute.test.ts)）

C3 校验的是**方案说得对不对**，这一层校验的是**执行有没有真的做到**。用例刻意绕过 C3 直接把方案喂给执行器，包括几条 C3 本来就会拦下的——那不是在测无效输入，是在证明**两层是独立的防线**。一条只在上游正确时才成立的防线，不叫防线。

| 变异 | 结果 |
|---|---|
| git 前置检查永远放行 | 失败 1/8 |
| 类型检查结果被忽略 | 失败 1/8 |
| `delete-file` 不换成空模块（回到 `removeSourceFile`） | 失败 1/8 |
| 导出数对账永远成立 | 失败 1/8 |
| 文件数对账永远成立 | 失败 1/8 |
| 对账失败不回滚 | 失败 2/8 |
| 磁盘删除空转 | 失败 3/8 |
| 符号定位失败时跳过而不是整条放弃 | 失败 1/8 |
| 改写结果不写盘 | 失败 2/8 |
| 原始实现 | 失败 0/8 |

第三行是端到端用例挖出来的真实缺陷。初版用 `project.removeSourceFile()` 让类型检查反映「文件没了」，**但那是无效的**——Project 建在真实文件系统上，从项目里移掉之后 TypeScript 仍会顺着 `import` 从磁盘把它读回来，于是删一个正被 import 的文件也能一路绿灯。改成在内存里替换为 `export {};` 之后这条变异才有东西可抓。

还有一条判据被变异测试**删掉**了：原本的 `survived.length === 0` 得到 0/8，不是断言漏了，是那个条件在逻辑上永远不会独立触发（`actual = deleted.length - survived.length`，`survived` 非空必然先让文件数等式不成立）。**一个永远由别人代劳的判据，留着只会让防线看起来比实际更厚。**

### 串起来之后（[tests/proposalflow.test.ts](../tests/proposalflow.test.ts)）

前四层各自都绿，不等于串起来还成立。

| 变异 | 结果 |
|---|---|
| 跳过静态校验，模型说什么就是什么 | 失败 3/6 |
| 候选池为空时也调用模型 | 失败 1/6 |
| 被拦下的方案不展示 | 失败 1/6 |
| 强制改写不留痕 | 失败 1/6 |
| 高风险方案不加警示 | 失败 1/6 |
| 不提示「没有全部执行」 | 失败 1/6 |
| 原始实现 | 失败 0/6 |

后四行测的都是**输出里必须说出来的话**：拦下了什么、改写了什么、哪条不安全、为什么不给全部执行。它们不影响任何一个字节的改动结果，但一个只展示成功结果的工具，没法让人判断它靠不靠谱。

这里也写坏过一条断言：初版用 `doesNotMatch(/全部执行/)` 去断言「不提供全部执行」这个设计决策。**用「输出不含某词」断言设计意图本来就脆**，而那四个字恰恰出现在声明不提供它的那句话里。改成正向断言「输出必须说出这句话」才对。

### 取消、超时与断线重连（[tests/jobs.test.ts](../tests/jobs.test.ts)）

这组守的是一句话：**「停止生成」如果只做前端，那是障眼法。** 关掉 EventSource 只是不看了，后台该跑还跑、token 照烧。所以断言的重点不是「界面停了」，而是**下游真的收到了 signal**。

| 变异 | 结果 |
|---|---|
| cancel 不真的 abort（只改状态） | 失败 1/16 |
| signal 不传给任务体 | 失败 1/16 |
| 取消后仍按 completed 收尾 | 失败 1/16 |
| abort 抛错时按 failed 处理 | 失败 1/16 |
| 超时定时器不装 | 失败 1/16 |
| 重复取消会覆盖原因 | 失败 1/16 |
| 事件不带 id | 失败 1/16 |
| 忽略 `Last-Event-ID`，重连全量重推 | 失败 1/16 |
| 脏 `Last-Event-ID` 不做兜底 | 失败 2/16 |
| 重连不补齐已生成文本 | 失败 1/16 |
| 原始实现 | 失败 0/16 |

**第一轮有四条 0/14，而且四条的成因各不相同**——这轮变异测试的收获全在这里：

| 假绿 | 真正的原因 |
|---|---|
| 事件不带 id | 事件有**两条出路**：实时推给已订阅的流、回放给新接入的流。我的用例全走回放，实时那条从没被看着 |
| abort 抛错按 failed 处理 | 「吞掉 abort 正常返回」和「abort 时抛错」是 `if/else` 的两边，我只测了一边。而真实的库（包括 ai SDK）走的是**没测的那边** |
| 重复取消覆盖原因 | 断言本身写错了：两次都用 `user` 取消，覆盖了也看不出来。改成先 `timeout` 再 `user`，原因仍是 `timeout` 才算数 |
| 超时不清理 | **这条是真的测不出来**，见下 |

### 一条诚实的 0/14

`clearTimeout(timer)` 删掉之后全部用例照样绿，这不是断言漏了：`cancel()` 里的 `status === "running"` 守卫已经兜住了状态正确性，漏清的定时器唯一后果是攥着 record 多活到超时时刻——**那是 GC 时机问题，测不出来**。

所以没有为它补一条假装能测的断言，而是把这个结论写进了 [src/tasks.ts](../src/tasks.ts) 的注释。**变异测试的结论有三种：断言漏了、实现里有死代码、以及这一种——后果真实存在但不可观测。** 混为一谈就会写出为了变红而变红的测试。

### 代码围栏的流式渲染（[web/tests/markdown.test.tsx](../web/tests/markdown.test.tsx)）

加代码围栏时最先坏掉的不是解析，是**分块边界**：代码块内部允许空行，而那条边界原本就是 `lastIndexOf("\n\n")`。切在围栏中间，已成块的部分就会留下一个没闭合的 ```——它会把后面所有内容一路吃到结尾。

**表格写到一半是局部重排，围栏写到一半是全局污染。**

| 变异 | 结果 |
|---|---|
| 分块边界不管围栏（回到 `lastIndexOf`） | 失败 1/31 |
| 围栏不优先于表格/标题解析 | 失败 6/31 |
| 正在写的代码块退回普通段落 | 失败 2/31 |
| 未闭合围栏不渲染（要求必须闭合） | 失败 1/31 |
| 不认语言也高亮 | 失败 1/31 |
| 关键字表不查 | 失败 1/31 |
| 注释规则排在字符串之后 | 失败 1/31 |
| 原始实现 | 失败 0/31 |

第二行 6/31 最高，因为围栏一旦不优先，里面的 `| a | b |`、`# 标题`、`- 列表` 会分别被当成表格、标题、列表——**一个位置错，三种块型一起错**。

### 一条写错的断言：高亮会切碎文本

三条用例第一次跑是红的，但实现没问题：语法高亮把 `const a = 1` 切成了三个 `span`，用整串正则去匹配原始 HTML 当然不中。

修法不是放宽正则，是加一个 `text()` 把标签剥掉——**断言"内容在不在"看纯文本，断言"结构对不对"才看 HTML**。两件事混在一个正则里，就会变成每次改渲染细节都要改测试。

### 桩模型的一个陷阱：假绿

写这组测试时，头一版桩模型漏了 `defaultObjectGenerationMode: "json"`。结果是：

```
not ok  正常方案原样返回          ← 真失败
ok      预测为 0 的方案进不来      ← 假绿
ok      缺少 prediction 的进不来   ← 假绿
ok      kind 不在枚举里进不来      ← 假绿
```

三条 `assert.rejects` 全绿，但它们通过的原因是「模型没有默认对象生成模式」这个**与被测逻辑毫无关系的错误**——schema 压根没来得及执行。

`assert.rejects` 这类断言天生容易假绿：**它只要求抛错，不要求抛对的错。** 补上那一行之后再跑，才是真的在测 schema。

这和变异测试是同一个主题：**绿灯不等于断言有效。**

### 变异测试抓到的一个真实缺口

第一轮跑「`unexport` 空转」时结果是 **0/5 失败**——断言全绿。

原因不是断言写错了，而是**那条代码路径根本没被执行到**：`unexport` 对变量和对函数声明走的是两个不同分支，而当时 fixture 里唯一需要 unexport 的符号 `internalPath` 是个变量，函数分支从未被触发。

补了 `src/format.ts`（一个只被同文件使用的导出函数）之后，这条分支才真正进入覆盖范围，同一个变异变成 3/5 失败。

**这正是做变异测试的意义**：它测的不是「断言写得对不对」，而是「断言到底有没有在看着那段代码」。

## 改造闭环的端到端用例

`pnpm eval` 校验的是**判定**，`pnpm test`（[tests/apply.test.ts](../tests/apply.test.ts)）校验的是**执行**——两件事不能混为一谈：返回值说「已应用」而磁盘没变，是最坏的一种绿灯。

每个用例都从 fixture 复制出一个真实的、已提交的 git 仓库，跑完再读回文件内容对账：

| 用例 | 断言的行为 |
|---|---|
| 纯类型环 | 磁盘上真的出现 `import type`，函数体原样保留，重跑分析环归零，diff 与报告落盘 |
| 模拟与实测对不上 | 注入两条源码里不存在的边制造预测偏差 → 必须还原到改动前，但 diff 要留档 |
| 运行时环 | 没有可拆的边，一个字节都不写，`git status` 保持干净 |
| 目标文件有未提交改动 | 拒绝执行，用户的改动原封不动 |
| 目标文件不受 git 跟踪 | 拒绝执行——没有可靠回滚手段就不动用户的代码 |

## 解析器替换前后

02–05 建立时全部是 `known-failure`，共同根因是 `src/graph.ts` 用正则而非 AST 提取符号与依赖。改用 ts-morph + TypeScript 模块解析后，四个用例同时转为通过：

| 用例 | 正则实现 | AST 实现 |
|---|---|---|
| `02-alias-cycle` | 0 依赖边，0 个环 | 2 依赖边，1 个环 |
| `03-dynamic-import-cycle` | 1 依赖边，0 个环 | 2 依赖边，1 个环 |
| `04-arrow-component` | 1/2 组件（漏 `Card`） | 2/2 组件 |
| `05-jsx-render-edge` | 无 render 边 | 产出 render 边 |
| **通过率** | **1/5（20%）** | **5/5（100%）** |

`02-alias-cycle` 那行最能说明问题：两个文件明明互相 import 构成环，正则实现扫出 3 个符号却是 **0 条依赖边**——alias 导入被整条丢弃，环自然无从谈起。
