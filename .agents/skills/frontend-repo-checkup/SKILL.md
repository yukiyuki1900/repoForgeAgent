# 前端仓库体检

用 RepoForgeAgent 的工具集做一次结构诊断，产出**带文件路径和行号的行动清单**。

核心原则：**先拿事实，再下结论。** 目录名、文件名、常见约定都会骗人——`utils/` 里塞着业务逻辑、`components/` 里放着请求封装，都是常态。

## 前置检查

确认工具可用。两条路径能力不同，先认清自己在哪条上：

| | 挂了 MCP（推荐） | 只有命令行 |
|---|---|---|
| 可用范围 | **任意项目**，server 启动时已绑定目标仓库 | 需要 cwd 在 RepoForgeAgent 仓库 |
| 查询 | `searchFiles` `listHotspots` `listCycles` `listDeadExports` `getDependents` `getDependencies` `getFileSummary` `findSymbol` `readSource` | `pnpm ask <repo> "问题"` |
| 报告 | 无——MCP 只出结构化数据 | `pnpm analyze <repo>` 出完整报告 |
| 改造 | **不可用**，刻意没接入 | `pnpm refactor <repo>`（拆环）<br>`pnpm refactor <repo> --dead-exports`（清理死导出） |

两者都没有就停下来告诉用户，**不要退回用 grep 猜**——那正是这套工具要取代的做法。

## 第 1 步：建立全局事实

**不要跳过这步直接读代码。** 没有全局依赖图的时候，你对「这个文件重不重要」的判断全靠猜。

**MCP 路径**——两个调用就够：

```
listCycles({})              // 有几处环、成员是谁
listHotspots({ limit: 10 }) // 谁被依赖得最多
```

需要文件总数、符号数、关系边总数时调 `refreshIndex`，它会在返回里带上这些规模统计。注意它是**重新扫描**，几百个文件要几秒，别在循环里调。

**命令行路径**：

```bash
pnpm analyze <repo>
```

拿到模块划分、循环依赖处数、维护性评分、关系边总数，外加一份 LLM 写的架构解读。

只关心某一类问题时加 `--query` 裁掉无关节点（例如 `--query "有循环依赖吗"` 会跳过架构解读，快很多）。

> ⚠️ 报告里有「执行计划」一节，列出本次**跳过**了哪些节点。看到某项分析缺失时先查这里——是没跑，不是没发现问题。

## 第 2 步：定位热点

```
listHotspots({ limit: 10 })
```

**一次拿到排行，不要逐个文件调 `getDependents` 去试。** 后者是最常见的浪费——实测有模型为了找「谁被依赖最多」连续调了 7 次 `getDependents`，而 `listHotspots` 一次就够。

读排行时按这两个信号分类：

| 形态 | 判断 | 典型问题 |
|---|---|---|
| 入边远高于出边 | 公共依赖枢纽 | 改动风险大，但本身未必有问题 |
| 出边也很高 | **职责过载** | 它既是底层依赖又依赖了上层，通常是重构起点 |
| 入边高但文件很短 | 桶文件（barrel） | 看它是不是只在 `export *`，是的话真正的问题在子模块 |

对排名前几的文件逐个 `getFileSummary`，确认行数与导出符号。**行数很少但入边极高 = 桶文件**，此时要 `readSource` 看它到底 re-export 了什么，否则会把「utils 被 69 个文件依赖」误读成「utils 很复杂」。

## 第 3 步：看分层有没有倒置

```
getDependencies({ path: "<热点文件>" })
```

前端项目的健康分层大致是：

```
pages / views  →  components  →  hooks / stores  →  utils / api  →  types
```

**依赖必须单向往下。** 如果 `utils` 出现了指向 `pages` 或 `components` 的边，那就是分层倒置——这通常是循环依赖的根源，也是最值得报告的结构问题。

发现倒置时要说清楚**具体是哪条边**：

> ✅ `src/utils/route/index.ts:12` 引用了 `src/router/routes.ts`，工具层反向依赖了路由层
> ❌ 「utils 层耦合度过高，建议解耦」

## 第 4 步：判断循环依赖能否自动修

```bash
pnpm refactor <repo>        # 只读，不写盘
```

输出会逐条说明每条环内边**能不能改成 `import type`**，不能改的会给出具体的值使用位置（如 `requestApi 在 content.ts:24 被作为值使用`）。

> ⚠️ **只挂了 MCP 的话这一步做不完整。** `listCycles` 能给出环的成员与真实回路，但「这条边能否安全改成 `import type`」依赖 refactor 的引用分析，没有暴露成 MCP 工具。此时如实说明：能定位环，但判不了可修性，需要在 RepoForgeAgent 仓库里跑一次 `pnpm refactor`。**不要自己读源码猜**——判断一个导入是否只在类型位置被使用，靠肉眼看会漏。

三种结论的读法：

- **有可拆边** → 建议用 `pnpm refactor <repo> --apply`，它会写入并做两道验证（类型不新增错误 + 环数与预测一致），任一不符自动 `git checkout` 回滚
- **全部不可拆** → **这是正常且有价值的结论**，说明这些是真实的运行时依赖，需要人做架构决策（提取共享模块、依赖倒置）。不要为了「有产出」而放松判定
- **没有循环依赖** → 直接说没有

> ⚠️ `import type` 在编译期被完全擦除，所以**它不算运行时依赖**。工具已经把这类边排除在环检测之外——看到「1 处循环依赖」时，那 1 处是真的。

## 第 5 步：找出没人用的导出

```
listDeadExports({})            // MCP：全仓的死导出
listDeadExports({ path: "src/utils/index.ts" })   // 只看某个文件
```

```bash
pnpm refactor <repo> --dead-exports     # CLI：连清理计划一起给出
```

真实项目里循环依赖可能只有一两处，**没人用的导出往往有几十个**，而且直接影响 tree-shaking。这一步的产出通常比第 4 步更实在。

读结果时注意两件事：

- **`stillUsedInsideFile`** 决定改法。为真只能去掉 `export` 关键字（声明还在被同文件使用），为假才可以整条删除。
- **判定是漏报方向的。** 包入口、框架约定导出（`getServerSideProps`）、被 `export` 转发的符号、默认导出、`.vue` 文件都不参与判定。**列出来的基本可信，没列出来的不代表活着**——不要反过来说「其余导出都有人用」。

> ⚠️ 清理有级联：删掉 A 之后，只被 A 用过的 B 才变成死代码。一轮不收敛，需要反复跑到没有新改动为止。

## 第 6 步：产出行动清单

按「影响面 × 修复成本」排序，每条必须包含：

1. **具体位置** —— 文件路径 + 行号
2. **事实依据** —— 入边数、环成员、值使用位置，而不是形容词
3. **可执行的下一步** —— 改什么，不是「优化一下」

模板（数字为示例，填你实际查到的）：

```markdown
### 1. src/utils/index.ts 是桶文件，被 69 个文件依赖

- 事实：20 行，仅 `export *` 转发 19 个子模块（src/utils/index.ts:1-19）
- 影响：任何子模块变动都会让 69 个文件的依赖图失效
- 建议：让只用到单个子模块的引用方改为直接引子模块，
  例如 `src/api/log.ts:3` 只用了 `format`，可改为 `@/utils/format`
```

## 反模式

这几条会让整份报告失去价值：

**❌ 没有落点的建议**

> 「utils 层职责不清，建议拆分」

拆成什么？谁先动？改完怎么验证？——都没说，等于没说。

**❌ 把目录名当职责**

看到 `components/` 就说是展示层。必须 `readSource` 确认。这套工具存在的理由就是目录名不可信。

**❌ 报告评分而不解释**

> 「维护性评分 56」

56 分意味着什么、哪个维度拖了后腿、怎么涨上去——不说清楚就只是个数字。

**❌ 越界猜测**

工具查不到的东西就说查不到。**编一个合理的答案比承认查不到糟糕得多**——报告一旦出现一处编造，读的人会怀疑全部内容。

## 什么时候该停下来问人

- **要动的是构建配置、路由表、状态管理这类全局文件** —— 影响面超出静态分析能覆盖的范围（运行时注入、动态路由都看不到）
- **环里全是运行时依赖** —— 怎么拆是架构决策，需要业务上下文
- **仓库是 monorepo** —— 当前只解析根目录 tsconfig，子包各自的 `paths` 可能没被解析，依赖图会缺边

- `docs/LIMITATIONS.md` —— 能力边界。报告里声称「没有发现 X」之前，先确认 X 在不在检测范围内
- `docs/DESIGN.md` —— 判定规则的依据，例如 `import type` 为什么不算运行时边
